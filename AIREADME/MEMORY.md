# MEMORY：ThermalPulse

> append-only。这里记录已经发生的事故、失败和踩坑，决策理由写入 DECISIONS。

当前为 pre-alpha。可复现失败按“现象、根因、结论/避免”记录，并附可验证证据边界。

## AppleSMC 参数结构在 Swift 中得到 76 字节 stride · 2026-08-28

- 现象：首个 ABI 单元测试发现 Swift 逐字段声明的参数结构 stride 为 76，不符合 AppleSMC user-client 的 80 字节调用边界。
- 根因：Swift 对 C ABI 尾部填充的布局不构成可靠承诺，逐字段宽度相加不能替代真实 C 结构布局验证。
- 结论/避免：结构迁到唯一 C bridging header，并用 `_Static_assert(sizeof(...) == 80)` 与 Swift 测试双重锁定。不要在 Swift 或其他文件复制近似结构。

## Apple Silicon `flt ` 按大端解码得到极小伪值 · 2026-08-28

- 现象：真实风扇 key 的类型为 `flt `，按大端 IEEE 754 解码后得到接近零的极小值，导致实际和最大 RPM 合理性测试失败。
- 根因：当前 Apple Silicon 的 `flt ` payload 使用小端字节序，而整数及 `sp` / `fp` 定点类型沿用大端规则。
- 结论/避免：按数据类型决定字节序，并为小端浮点增加固定向量单元测试；实机验收必须同时校验实际 RPM、最大 RPM 与二者关系，不能只看调用成功。

## 扫描完成时 SwiftUI `List` 触发 NSTableView 重入警告 · 2026-08-28

- 现象：首次 App 冒烟启动后，一次性扫描结果刷新动态 `List` 时出现 NSTableView delegate reentrant operation 警告，并提示未来系统可能升级为断言。
- 根因：macOS SwiftUI `List` 基于 NSTableView，扫描结果一次插入大量候选行时触发了表格委托重入路径。
- 结论/避免：监控读数改用 `ScrollView` 与 `LazyVStack`，再次启动并完成扫描后不再出现警告。实时高频数据视图不默认使用 `List`。

## Release 长测约第 10 分钟出现未归因性能台阶 · 2026-08-29

- 现象：最终 Release App 的前 10 个一分钟监督样本中，`top` CPU 均值为 3.8%、物理内存均值为 213.3 MiB；第 11 个样本起抬升，后 50 个样本 CPU 均值为 13.0%、物理内存均值为 312.2 MiB。进程继续运行至 3605 秒，日志为空，RSS 没有持续单调上升。
- 根因：未知。长测期间允许用户操作曲线窗口，但没有记录界面动作时间戳，因此不能确认台阶来自展开高级候选、切换时间范围、重开窗口、Swift Charts 分配或其他原因。
- 结论/避免：后续性能验收要同时记录窗口状态、选择集合、时间范围和动作时间点，再与区间 CPU、内存对齐。缺少关联证据时，分段报告数据，不把台阶归因于某个具体交互。

## Release 无操作 12 分钟基线未复现性能台阶 · 2026-08-29

- 现象：加入本地性能标记后，Release App 在窗口可见、3 条默认曲线、5 分钟范围、原始候选收起且无任何交互的条件下运行 12 分钟。13 个 `top` 样本的 CPU 均值为 6.52%，范围为 4.9% 至 10.7%；内存均值为 211.62 MiB，范围为 206 至 215 MiB。第 10 分钟 CPU 为 9.0%，第 11 分钟回落至 5.3%，没有同步内存跃升。
- 根因：仍未定。本次反证表明“Release 无操作运行到约第 10 分钟必然触发台阶”不成立，上一轮现象更可能与当时交互状态、旧构建的运行条件或外部负载有关，但暂时不能区分。
- 结论/避免：后续使用单变量阶段，分别只展开原始候选、只切换到 1 小时、只重开窗口和只改变曲线选择，每段保留事件时间与区间资源样本。无操作基线未复现不等于原问题已解决。

## Tp 候选数量不能解释为 P 核数量 · 2026-08-29

- 现象：当前 Mac16,7 枚举到 102 个有效 `Tp` float 温度候选，远大于物理 P 核数量；其中最高 key 还会随负载变化。
- 根因：`Tp` 是动态温度传感器族前缀，不是一个“每个 P 核恰好一个 key”的公开稳定表。AppleSMC 又没有公开逐 key 语义，单看命名和数量无法建立具体核心映射。
- 结论/避免：只对整族计算平均值、最高值和候选数量，并用短时负载验证响应；界面写“P 核温度候选族”，不得把 102 写成核心数，不得给单个 key 编造核心编号。跨机型仍需重新验证。

## SMAppService 首次查询的 notFound 不等于 bundle 配置丢失 · 2026-08-29

- 现象：签名 Debug App 的 LaunchDaemon plist 和 helper executable 都位于正确 bundle 路径，`SMAppService.status` 首次仍返回 `notFound`，界面因此误报“当前 App 包内没有找到 Turbo helper 配置”。
- 根因：`status` 描述系统已经记录的服务状态，不验证 bundle 内 plist 是否存在。Apple DTS 的最小示例在注册前同样得到 raw status 3，调用 `register()` 后成功；`notFound` 在首次注册前可表示系统尚不知道该服务。
- 结论/避免：`notRegistered` 与首次 `notFound` 都可进入显式注册流程，但仍必须由用户确认后调用 `register()`。判断 bundle 布局要独立检查产物，不能从首次 status 反推 plist 缺失。

## HardwareProbe scheme 被 Debug configuration 覆盖后静默跳过 · 2026-08-29

- 现象：命令选择了 `ThermalPulseHardwareProbe` scheme，却又显式传入 `-configuration Debug`，结果硬件集成测试被普通测试环境门禁跳过，看起来像探针运行成功但没有产生真实设备证据。
- 根因：scheme 的 HardwareProbe configuration 被命令行 configuration 覆盖，测试进程没有获得硬件探针开关。
- 结论/避免：运行只读实机探针时使用 scheme 自带 configuration，不额外传 `-configuration Debug`；必须从 xcresult 确认探针实际通过，而不是只看 xcodebuild 退出码。

## 当前 M4 Pro 没有旧式全局 FS 模式 key · 2026-08-29

- 现象：当前 Mac16,7 读取旧式 `FS! ` 返回控制器错误 0x84，但 `F0Md`、`F1Md` 和 `Ftst` 都能稳定读取为 1 字节 `ui8 `；两个 `F{i}Tg` 与 `F{i}Mx` 都是 4 字节 `flt `。
- 根因：风扇控制 key 与数据类型会随平台变化，旧 Intel 或其他机型实现不能直接套用到当前 Apple Silicon。
- 结论/避免：模式 key 必须按动态风扇索引解析 `F{i}Md` 或 `F{i}md`，先验证类型和值；目标写入复制实时 `F{i}Mx` 原始字节。`FS! `、风扇数量和 RPM 都不得硬编码，全程先用只读探针建立目标机证据。

## 沙箱内 codesign 可能制造证书不受信任假象 · 2026-08-29

- 现象：加入新 helper 写入源码后的 Personal Team Debug 构建由 Xcode 成功产出，但在受限沙箱内对 App 与 helper 执行 strict 验证都返回 `CSSMERR_TP_NOT_TRUSTED`；对同一产物在沙箱外重跑后，两者都通过并满足 designated requirement。最终源码重新签名构建后也得到相同的沙箱外通过结果。
- 根因：受限执行环境无法完整访问系统证书信任服务，codesign 把环境限制表现为证书链不受信任，并非产物签名损坏。
- 结论/避免：签名完整性仍需独立验证，但出现 `CSSMERR_TP_NOT_TRUSTED` 时先用完全相同的只读命令在沙箱外复现，再决定是否阻断。构建、strict、系统注册、root 启动、XPC 实连和真实 SMC 写入继续分开验收。

## SMAppService 同步注销后立即注册留下未注册状态 · 2026-08-29

- 现象：用户授权升级 helper 后，App 同步调用 `unregister()` 再立即调用 `register()`。旧 root helper 被系统移除，但 App 显示升级失败，`launchctl` 确认 system 域没有新服务，租约文件仍不存在。
- 根因：注销与系统完成服务移除之间存在完成时序。同步 API 返回后立即重注册触发竞态，不能把两次调用顺序等同于系统生命周期已经完成切换。
- 结论/避免：使用 `SMAppService` 的异步 `unregister()` 并等待完成后再注册，升级前先失效旧 XPC。失败后先只读刷新实际注册状态，再从 notRegistered 明确重试；不要用延时猜测、手工 launchd 命令或直接覆盖文件补救。

## 首次真实 Turbo 在读回门禁失败并自动回退 · 2026-08-30

- 现象：启动前专用只读门禁确认两台风扇均为 automatic 且 `Ftst=0`。用户确认短时 Turbo 后，监控曲线观察到最高约 2234 RPM 的短时上升，但 helper 返回 failed-safe-auto 与 readback mismatch，没有进入 active。失败后持久租约已删除；独立 HardwareProbe 读回 `F0Md=0`、`F1Md=0`、`Ftst=0`、`F0Ac=1350.73 RPM`、`F1Ac=1462.07 RPM`，目标值也已回到苹果自动控制值。
- 根因：尚未确定。当前有限错误只说明模式、最大目标或实际 RPM 上升门禁之一不一致，不能从曲线中的单个峰值判断两台风扇是否都满足条件。较早的一次全量枚举还短暂读到 `F0Md=3`、`F1Md=3` 与两个实际 RPM 为 0，而紧接着的专用点读门禁通过；该非原子快照可能相关，但不是已证实根因。
- 结论/避免：本次可以确认失败保护后的 automatic 恢复，不能确认 Turbo 成功。下一次真实写入前先增加逐风扇、逐阶段、无设备标识的有限诊断，区分模式、目标和实际 RPM 失败点；完成新签名 helper 升级后再次取得用户明确授权。失败后不自动重试，也不以曲线峰值替代全部模式、目标和实际 RPM 读回。

## 第二次 Turbo 短转后系统接管，旧 helper 留下 lease · 2026-08-30

- 现象：用户点击升级后启动 Turbo，风扇只短时转动。helper 日志先记录两个动态风扇的激活和 `Ftst` 接管，约 7 秒后记录风扇 0 的模式读回为 automatic，随后进入恢复。600 秒截止后，helper 每秒持续报告 `restoration_failed`，`/Library/Application Support/ThermalPulse/turbo-lease.plist` 仍以 root 0600 存在。
- 根因：已确认恢复模型缺陷，尚未确认激活失败的全部硬件时序。旧恢复实现无条件写 mode 0 与 `Ftst=0`，即使系统已经把风扇接管为 mode 3、`Ftst` 已为 0；冗余写入被拒绝时，helper 把安全的 system 状态误判为恢复失败并保留 lease。激活路径的模式写入返回成功后也没有立即读回，可能允许瞬时成功但未保持的模式继续到后续阶段。
- 安全证据：独立普通权限 HardwareProbe 读回 `F0Md=3`、`F1Md=3`、`Ftst=0`、`F0Tg=0`、`F1Tg=0`、`F0Ac=0 RPM`、`F1Ac=0 RPM`，两台风扇最大值仍为 5777 RPM。该证据说明硬件当前由苹果 system 模式接管，不说明旧 helper 完成了恢复，因为 lease 仍存在。
- 结论/避免：mode 0 与 mode 3 都视为 Apple 管理，恢复先读后写，Apple 已接管时跳过冗余 mode 写入，`Ftst` 已为 0 时跳过冗余清除。手动模式和 `Ftst=1` 每次写入后立即读回。恢复失败日志区分 fan mode、actual RPM、thermal manager unlock 与 lease removal。协议升级到 v3 以强制显式 helper 升级。旧 lease 清理、修复版 helper 升级和新签名完成前禁止再次 Turbo。

## Personal Team 代码签名身份暂时不可用 · 2026-08-30

- 现象：普通无签名构建和定向测试通过，但签名 Debug 构建报告找不到匹配 Personal Team 的 `Mac Development` 私钥；`security find-identity -v -p codesigning` 返回 0 个有效身份。历史签名 App 仍能读到非空 Team ID，但 Authority 已不可用。
- 根因：未确定，可能与免费开发签名的短期有效期或本机钥匙串状态变化有关。没有证据时不能归因于源码或自动修改工程签名设置。
- 结论/避免：允许继续无签名构建、测试和只读硬件探测，但不得用 ad hoc 构建替换已注册 helper。先在 Xcode 恢复有效 Personal Team 开发签名，再重新构建并独立验证 App、helper identifier、Team ID 与 strict 签名；helper 系统升级仍需用户单独确认。

## P 核全族平均在空闲时出现不自然跳变 · 2026-08-30

- 现象：菜单栏的 P 核温度持续在约 20 °C 与 40 °C 间跳变。实现每秒把 102 个有效 `Tp*` float 候选直接求算术平均。
- 根因：`Tp*` 是当前机器上范围很大的动态热区族，不是 102 个物理 P 核。空闲、核心休眠或占位热区的低值会改变全族平均，平均本身没有稳定的物理语义。12 秒只读追踪还确认公开 M4 Pro 列表中的 8 个 P 核 key 在当前 Mac16,7 全部固定为 40.0 °C，不能照搬 Mac16,8 的逐 key 表。
- 结论/避免：P 核与 E 核只接受 10 至 120 °C 的有效动态族候选，面向用户显示族内当前热点；电池继续显示两枚已验证 key 的平均。不要用平滑动画掩盖错误聚合，也不要把其他 M4 Pro 的 key 表当成本机事实。

## `Ftst` 异步生效晚于立即读回并留下无租约占用 · 2026-08-30

- 现象：升级协议 v3 helper 后，用户点击启动，App 很快进入状态异常。helper 日志记录 `activation_started`，约 2 秒后记录 `restoration_completed issue=modeReadbackMismatch`，没有记录 `thermal_manager_unlock_claimed`。随后独立只读读回 `F0Md=0`、`F1Md=0`、`Ftst=1`，而 root 租约文件不存在。
- 根因：helper 写 `Ftst=1` 后立即读回，读到了异步写入生效前的旧值 0，于是进入恢复。旧恢复逻辑又在异步写入真正生效前读到 0，跳过清除并删除租约；稍后硬件才变为 1。
- 安全证据：两台风扇当前均为 automatic mode 0，没有留在手动模式；但 `Ftst=1` 仍未恢复，因此不能宣布安全恢复验收通过，也不得再次启动 Turbo。
- 结论/避免：协议升级到 v4。接管写 1 后等待 3 秒再读回；租约记录过接管时，恢复无条件写 0，等待稳定读回后才删除租约。无租约 `Ftst=1` 不能由普通启动路径自动清除或当作自有状态，当前遗留值需要单独授权恢复并再次只读验收。

## 异步注销完成后立即注册仍返回错误 1 · 2026-08-30

- 现象：重启后只读硬件门禁确认 mode 3、`Ftst=0` 且无租约。旧 v3 helper 随后重新连接，App 显示协议不兼容。用户确认升级后，ServiceManagement 注销返回成功，但约 5 毫秒后的注册返回错误 1；旧 helper 已退出，system 域没有新 helper，界面一度仍保留注销前的不兼容信息。
- 根因：`unregister()` 的异步完成只证明注销请求完成，不能证明 `SMAppService.status` 和系统服务记录已经经过稳定观察。当前代码把回调完成直接当成可立即重新注册的充分条件。
- 结论/避免：注销后连续观察 `notRegistered` 或 `notFound` 稳定，再执行一次注册；超时或失败不自动重试。升级错误日志只记录错误域、错误码和原始状态。界面状态必须以重新读取的注册状态为准，不能把旧 XPC 的协议不兼容提示解释为当前仍有 helper。
- 后续验证：包含稳定替换门禁的当前构建由用户从 `notRegistered` 状态显式注册后，ServiceManagement 返回成功，root helper、Mach endpoint 和双向签名 XPC 均已读回；租约不存在，注册后只读门禁确认两台风扇为 mode 3 且 `Ftst=0`。本次只确认从未注册状态安全登记当前 v4 helper，没有重新执行已注册 helper 的替换路径，也不代表 Turbo 写入链路已经验收。

## 实际 RPM 小幅超调被旧验收误判，active 文案仍显示苹果自动 · 2026-08-30

- 现象：已注册 v4 helper 首次成功进入 active，独立探针确认两台风扇 mode 1、目标原始字节等于 5777 RPM 最大值，实际转速接近全速。验收仍出现两条失败，因为风扇 0 的最高实际值为 5854.90 RPM，风扇 1 为 5778.31 RPM，略高于标称最大值；菜单栏逐风扇行同时继续显示“苹果自动控制”。
- 根因：测试把控制目标上限与实际传感器反馈混成同一个绝对上限，忽略闭环控制和浮点读回可能产生的小幅超调。逐风扇说明文字又是视图中的硬编码，没有映射 `TurboStatus.phase`。
- 安全证据：主动停止后独立读回两台风扇均为 mode 3、`Ftst=0`，root lease 不存在；helper 日志记录 `restoration_completed issue=none`。本轮没有自动重试 Turbo。
- 结论/避免：最大目标仍要求复制并精确读回动态 `F{i}Mx` 原始字节；实际 RPM 单独使用动态最大值 105% 的可信上限，启动门禁、active watchdog 与 HardwareProbe 复用同一策略。界面控制文案必须来自可信 Turbo 状态。安全语义变化提升协议版本，避免已安装旧 helper 被误当成已经包含修复。

## 稳定 P 核代表 key 的 0 哨兵污染温度曲线 · 2026-08-30

- 现象：P 核卡片温度正常，但固定 5 分钟曲线周期性垂直跌到 0 °C，E 核和电池没有同步变化。
- 根因：卡片每秒从全部有效 `Tp` 候选取热点并过滤 10 至 120 °C，曲线则读取会话开始时选定的单个稳定代表 key。该 key 返回的 0 能通过通用有限数值检查并进入原始环形缓冲，显示层此前没有复用核心温度合理范围。
- 结论/避免：P 核与 E 核历史在展示边界过滤 10 至 120 °C 之外的点，并让现有间隙分段逻辑形成断线。不要把哨兵替换为 0、上一值或平滑结果，也不因一个代表 key 的瞬态无效改写原始历史。

## `MenuBarExtra` 复合标签只显示第一个文本 · 2026-08-30

- 现象：状态栏标签用 `HStack` 包含两个双行 `VStack`，源码表达了 P 核、电池和两台风扇，实际菜单栏却只显示左上角 P 核温度。
- 根因：当前 macOS 26 的 `MenuBarExtra` 状态项宿主没有按普通 SwiftUI 视图保留该复合标签，实际结果只呈现第一个 `Text`。编译成功不能证明状态项宿主会完整渲染复合子树。
- 结论/避免：需要多行菜单栏摘要时使用单个 `Text(verbatim:)` 和明确换行，让系统只接收一个文本渲染原语。2×2 排列用等宽文本中的两行内容表达；真实状态栏外观继续保留人工验收门禁。

## 8 pt 双行状态项在实际菜单栏中过宽 · 2026-08-30

- 现象：单个多行文本已经显示 P 核、电池与两台风扇，但 8 pt 字号配合 `F1/F2` 标签后，实际状态项仍过大，菜单栏无法容纳。
- 根因：源码中的小字号不等于状态项整体足够紧凑，四组标签、空格和四位 RPM 数值共同决定常驻宽度；编译和签名验证不能替代真实菜单栏尺寸验收。
- 结论/避免：常驻状态项使用 6 pt 等宽字体和位置语义，温度压缩为 `P/B` 前缀，右列省略重复风扇标签与单位。完整语义留在展开面板和辅助功能描述，每次状态项布局变化都需要实际菜单栏人工确认。

## `MenuBarExtra` 忽略多行文本字号并裁掉顶部 · 2026-08-30

- 现象：状态摘要已经压缩为 `P69° 0` 与 `B27° 0` 两行，并在源码设置 6 pt 字号和负行距；真实菜单栏仍以明显更大的系统字号显示，顶部被裁掉，内容无法完整看见。
- 根因：当前 macOS 26 的状态项宿主会重新解释 `MenuBarExtra` 标签中的多行 SwiftUI `Text`，源码字体和行距修饰没有成为最终像素边界。编译、签名和进程存活都无法证明真实菜单栏布局。
- 结论/避免：需要严格尺寸的多行状态摘要不能继续交给状态项做文本布局。先用 AppKit 在固定高度模板图片中按固定字形和坐标绘制，再把单张图片交给 `MenuBarExtra`；视觉变化必须读取真实菜单栏或由用户截图验收。初始 16 pt 高、6.5 pt 字形虽完整但实际菜单栏中过小，随后调整为 18 pt 高、7.5 pt 字形。
- 后续现象：切换到新的签名 App 实例后，状态栏持续显示占位符，直到第一次展开面板。原因是只读采样只挂在面板 `onAppear`，状态栏标签本身没有触发采样。
- 结论/避免：菜单栏摘要依赖的数据采集必须随状态栏标签出现启动，不能依赖用户是否展开面板；两个入口共用 `startIfNeeded()` 保持幂等。

## 7.5 pt 固定图片完整但仍略小 · 2026-08-30

- 现象：18 pt 高模板图片已经完整显示 P 核、电池和两台风扇，实际菜单栏截图没有裁切，但用户确认 7.5 pt 字形仍偏小，并要求常驻摘要改为 P 核与 E 核温度。
- 根因：上一轮尺寸优先保证完整性，只比 6.5 pt 增加 1 pt，实际菜单栏中的可读性提升有限；电池温度又占用了 CPU 对比位置。
- 结论/避免：在固定图片边界内把字形提高到 8.5 pt、总高度提高到 20 pt，两行固定为 0 与 10 pt；左列使用 `P/E`，电池留在展开面板。每次调整后仍需真实菜单栏截图确认完整性与占位。

## 8.5 pt P/E 摘要仍可继续放大 · 2026-08-30

- 现象：20 pt 高模板图片完整显示 P/E 与两台风扇，用户确认布局正确，但仍希望字号再大一点。
- 根因：固定图片已经解除系统字号重排限制，当前剩余问题只是 8.5 pt 的视觉尺寸，没有内容缺失或列宽不足。
- 结论/避免：同一渲染器上调到 22 pt 高、9.5 pt 字形与 11 pt 行高，并继续用真实菜单栏截图检查上下边界；不借字号调整改变传感器聚合、风扇枚举或 Turbo。

## Turbo 的固定 `Ftst` 等待增加无必要启动延迟 · 2026-08-30

- 现象：已验收的真实 Turbo 日志从 `activation_started` 到 `thermal_manager_unlock_claimed` 固定经过约 3.1 秒，再到两台风扇实际 RPM 上升约需 5 至 6 秒。界面在整段时间都显示“正在验证风扇与安全租约”，容易让用户认为租约检查本身需要近 9 秒。
- 根因：协议 v4 为规避 `Ftst` 异步写入后立即读到旧值，在接管和恢复后都无条件等待 3 秒。启动路径可以用稳定读回更早证明状态，但风扇物理起转仍需要保留实际 RPM 趋势验证。
- 结论/避免：接管写 1 后每 100 毫秒读回，连续两次为 1 就继续，3 秒内仍不稳定则失败恢复。不缩短恢复路径的 3 秒窗口，不降低模式、目标或实际 RPM 门禁。界面改为“正在接管并等待风扇起转”。仅构建新的已签名 App 不会更新已注册 root helper，需要用户单独授权升级后才会在真实 Turbo 中生效。
- 协议隔离：优化后的 App 与内嵌 helper 使用协议 v6，当前系统仍运行旧 v5 helper。v6 App 已按不兼容状态拒绝旧 helper，本轮没有升级系统服务或执行 Turbo。这样可以避免新 App 把旧固定等待实现误认为已经包含优化。

## 恢复失败测试只证明保留租约，没有证明看门狗重试 · 2026-08-30

- 现象：`testRecoveryFailureKeepsLeaseForWatchdogRetry` 的名称声称覆盖看门狗重试，实际只让停止恢复失败并断言租约仍存在，没有调用 `watchdogTick()`。生产代码的 watchdog 又只在 600 秒截止时间到期后触发恢复，因此截止前的 failed-safe-auto 不会按 300 毫秒节拍重试。
- 根因：测试把“保留了可供重试的租约”误当成“重试已经发生”，没有验证从恢复失败到解除故障后回到 inactive 的完整状态转换。这是测试名制造的假绿。
- 结论/避免：安全恢复测试必须对照最终状态和副作用，不只验证中间资源存在。新用例先制造恢复失败，再在截止前解除故障并调用下一次 watchdog tick，断言返回 inactive、租约删除且全部模式为 Apple 管理。生产逻辑同步改为 failed-safe-auto 且租约存在时立即恢复。

## 未知 `Ftst` 不能通过写入探测所有权 · 2026-08-30

- 现象：启动前若 `readThermalManagerUnlock()` 返回 nil，旧逻辑没有立即拒绝。后续手动模式写入若返回 thermal manager busy，控制器仍可能调用 `writeThermalManagerUnlock(true)`，对身份和占用都未知的 key 执行写入。
- 根因：能否声明 `Ftst` 所有权被推迟到写风扇失败后的补救分支，nil 没有与明确 false 区分，违反不确定状态禁止写入的红线。
- 结论/避免：只有明确读回 `Ftst=0` 才能允许接管；nil 直接返回 unsupported hardware，不能创建租约或写解锁 key。即使后续风扇写入返回 busy，也只能在本次启动已经证明 `Ftst=0` 时尝试接管。新增两组测试分别覆盖启动前未知和 busy 后未知路径。

## 状态轮询不能占用停止请求的唯一 XPC 槽位 · 2026-08-30

- 现象：active 期间 App 每秒调用状态查询，用户点击停止时如果前一次查询仍未回复，单请求 transport 会把停止判为通信失败，或由较晚返回的轮询结果覆盖停止状态。
- 根因：持久 XPC 连接错误地等同于同一时刻只能有一个业务请求；请求级 continuation、超时和连接级失效没有分层。
- 结论/避免：同一签名持久连接按请求身份分别保存 continuation 和超时任务。单个 reply 只结束自身请求，连接失效才统一失败剩余请求；停止前取消轮询，await 返回后再检查取消状态，避免旧 active 响应覆盖停止结果。

## M5 单风扇使用小写模式 key，且探测时已有外部手动控制 · 2026-08-30

- 现象：第二台 Mac17,2、Apple M5 MacBook Pro 的普通权限探针只读回 1 台风扇，模式 key 为小写 `F0md`，不是首台机器上的 `F0Md`。探测时 mode 为 1，目标等于 6550 RPM 动态最大值，实际约 6559 RPM，说明风扇已经由其他控制器置于手动模式。
- 根因：AppleSMC key 大小写和风扇数量会随机型变化，不能从 Mac16,7 双风扇布局或大写 `Md` 推导其他 MacBook Pro。只读探针不会识别外部工具名称，也不能把现有手动状态归因给 ThermalPulse。
- 结论/避免：模式 key 必须继续在 `F{i}Md` 与 `F{i}md` 中动态发现，菜单栏按实际风扇数量布局。外部 manual mode 是 Turbo 的明确拒绝条件，不能为了验收而抢占或自动恢复；本次只确认 M5 只读监控和单风扇 UI 数据链路，不确认 M5 Turbo。

## M4 专属候选 key 让通用硬件刻画产生假失败 · 2026-08-30

- 现象：产品温度聚合已经按有效 `Tp*` 与 `Te*` float 候选动态归组，但 12 秒 HardwareProbe 仍先用一组 M4 Pro key 断言 P 核和 E 核存在。M5 实际使用的代表 key 不在该表中，完整硬件刻画会把有效设备误判为不支持。
- 根因：早期设备研究用例混合了历史候选表与产品契约，后续产品逻辑通用化时没有同步移除测试中的机型知识。
- 结论/避免：硬件刻画必须调用与产品相同的 `ComponentTemperaturePolicy.matchingReadings`，按动态族验证并打印证据。机型 key 只属于一次性研究记录，不能成为跨 Apple Silicon MacBook Pro 的通过门槛。
